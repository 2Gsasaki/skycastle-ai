# 天空の城 越前大野城 AI予報：2026年9月15日の調査結果と改善点

この文書は、2026年9月15日時点のコード・CSV・Git履歴・Open-Meteo APIを調べた記録。数値はこの日の状態であり、1か月後には増える。**この日に予測コード、モデル、公開ページ、データは変更していない。** この文書だけを新規作成した。

## まず読む結論

- 最優先で確認する問題は、14日予報の最初の日の「前日」の天気が、履歴の最新行から無条件に取られること。2026年9月15日時点では、予報の最初は9月15日、履歴の最新行は9月16日で、**未来の日を前日として使う**。影響はまず最初の予報日に出る。これだけで最近の霧予測の連続した外れを説明できるとは限らない。
- 霧の予測は強く外れている。Gitに残る当日0時より前の予報を直近30日（8月17日～9月15日）で数えると、「霧海の予感」が20日、実際に霧を記録した日は0日。観測後に `history.csv` に残った「FogOnly」は同じ30日で15日。**前夜の予報と観測後の判定を混同しない。**
- 最後のモデル更新は2026年2月12日。学習時は348件中139件（約40%）が霧だったが、2月13日～9月15日の毎日の観測215件では霧の記録が0件。後者は現在のモデルに反映されていない。古いデータは天空の城の出現日とその前日を意図して集めたため、毎日の記録とは出現割合が違う。AI入力には月・季節がない。
- 城の正確な座標に変えても、今回試したAPIの計算地点は変わらなかった。座標変更だけで予報の大きなズレが直るとは言えない。
- 修正後の「天空の城チャンス」の的中率を80～100%にできる保証はない。予報する日を減らして的中率だけを上げると、出現日を見逃す可能性がある。**予報件数、的中件数、見逃し件数を一緒に測る。**

## プロジェクトと観測記録の前提

このプロジェクトは、越前大野城が雲海に浮かぶ「天空の城」の出現を予測する。公開ページは <https://2gsasaki.github.io/skycastle-ai/forecast.html>。表示名は、城が出やすい場合「天空の城チャンス」、城は見えなくても霧が出そうな場合「霧海の予感」。表示名は分かりやすく、現時点では名前より判定を直す方が重要。

ユーザーによる記録の説明：2015年11月22日～2025年10月23日のデータには、天空の城が出た日と、放射冷却・前日の雨や雪を調べるために意図して記録した前日の天気が含まれる。2025年10月27日以降は毎日の天気、霧の有無、天空の城の有無を記録している。天空の城の出現は年間およそ10回。前日が雨・雪でも翌日に出現し得る。一方、**城を観察するときには晴れ、雨が降っていれば見えない**という現地経験がある。午前0～1時の雨は出現しにくいという体感もあるが、後述の時間別API値だけで一律0%にする根拠は得られていない。

`data/history.csv` は9月15日時点で564行。うち2025年10月27日～2026年9月15日の観測は324件、天空の城を確認した日12件、霧のみ5件。9月16日の未来の予報行を含めると325行になるため、観測件数は324件と数える。`event=Castle` は41件、実際に城を確認したのはそのうち9件で、**41日予想／9日的中＝22.0%**。確認できた12日のうち9日を予想できた。

過去側の2015年11月22日～2025年10月23日は239行で、`castle_visible=1` が86行。**86行すべての直前の行は日付が1日前**だった。過去側の `castle_visible=0` は153行あり、単純に「出現日だけのデータ」とは扱わない。日付の飛び方は意図した収集方法と関係する。

## 現在の予測の流れ

1. `fetch_weather.py` と `fetch_forecast_window.py` が Open-Meteo の緯度35.98・経度136.49の時間別データから、日本時間の5・6・7・8時の気温、湿度、10m風速、雲量、降水量をそれぞれ平均する。14日予報は `.github/workflows/skycastle-auto.yml` で `--days 14` を指定する。
2. `score_fog.py` が気温・湿度から露点を求め、霧スコアと城スコアを計算する。
3. `train_model.py` は `history.csv` の `fog_observed` と `castle_visible` を教師データとして、霧用と城用の2本の LightGBM モデルを学習し、組み合わせた出現率を調整するモデルも作る。毎日の予報では `predict_model.py` と `predict_forecast_window.py` が**保存済みモデル**を読み、毎日自動で再学習はしない。
4. AI入力は当日の気温・湿度・風・雲量・降水量、直前の行の同じ5項目、前の気温との差。**霧スコア、城スコア、露点差、月・季節はAI入力に入っていない。** `docs/04_Fog_Castle_Score_Guide.md` にはスコアや露点差がAIへ直接渡るように読める記述があり、実コードと違う。説明書の「263行」も古い。
5. 城の総合出現率が50%以上なら `Castle`、それ未満で霧の確率が50%以上なら `FogOnly`、それ以外は `None`。公開ページ `public/forecast.html` は `event` により表示名を決め、`public/data/forecast_predictions.json` を読み込む。

9月16日の `data/feed.json` は城スコア95.5点に対し総合出現率3.4%、`FogOnly`。**スコアとAIの確率は別の計算**であり、高スコアがそのまま高確率を意味しない。

## 確認したコード・データ上の問題

### 1. 予報の「前日」が未来の日になる

`predict_forecast_window.py` の `build_feature_frame()` は、`history.csv` の日付順の最新行を最初の予報日の前日として使い、2日目以降は予報の直前の日を使う。最新履歴の日付が最初の予報日より前か、ちょうど1日前かは確認しない。9月15日時点の `data/forecast_window.json` は最初が9月15日、履歴の最新行は9月16日。**9月15日の前日には本来9月14日の値が必要**。`predict_model.py` の単日予測は対象日より前の行を選ぶため、この問題は主に14日予報側にある。さらに、予報対象の日付が履歴にあると `predict_forecast_window.py` は天気・確率・eventを履歴の値で上書きする。前夜の予報を評価するときは、最新のJSONだけでなくGitに残る当時のJSONを使う。

### 2. 霧の予測が季節と収集方法に合っていない可能性

2026年2月12日のモデル更新コミットは `e99056b1`。そのコミットの学習用CSVは348件、霧139件、城98件。古い239件は霧122件（約51%）、2025年10月27日～2026年2月12日の毎日記録109件は霧17件（約16%）。その後2月13日～9月15日の毎日記録215件は霧0件だが、モデルに入っていない。古い記録は意図して出現日の周辺を集めているため**データが悪いという意味ではない**。ただし、霧の発生割合を日常の予報にそのまま当てはめると高めに予想し得る。`train_model.py` の入力には月・季節がなく、学習に使わない日で霧予測を検証する処理もない。原因として有力だが、モデル内部の重要度は未確認。手元のPythonでは LightGBM 読み込みに必要な `libomp.dylib` がなく、モデル内部を読み取れなかった。ユーザーの指示によりプロジェクト外の環境は更新していない。

### 3. 前夜の予報と翌朝の天気のズレだけでは説明できない

Gitの `data/forecast_predictions.json` と `data/forecast_window.json` の履歴から、各日の日本時間0時より前の最新コミットを当時の予報として調べた。直近30日（8月17日～9月15日）は前夜の `FogOnly` が20日、観測された霧は0日。朝7時より前の最新コミットで数えても20日だった。20日のうち11日は、後から記録された履歴側の判定も `FogOnly`。つまり、**気象予報が更新された後も霧判定が残った日がある**。前夜の予報と観測後の記録の朝5～8時平均の差の中央値は、FogOnlyの20日で気温0.5℃、湿度3.38ポイント、風2.31 km/h、雲量21.75ポイント、降水量0 mm。雲量のズレはあるが、これだけで全20件の外れを説明できない。履歴側の天気はAPIの過去データに基づく値であり、現地で時間ごとに直接測った数値ではない。`fog_observed` はユーザーの観測結果として扱う。

例：9月10日の前夜予報（9月9日21:55頃）は `FogOnly`、霧確率97.3%。予報の朝平均は湿度85.75%、雲量47.75%、雨0。履歴の朝平均は湿度91.0%、雲量87.0%、雨0で、霧確率82.7%、`FogOnly`。実際の霧記録は0。9月5日も前夜の霧確率95.3%、観測後の履歴の霧確率88.2%、実際の霧記録0。

### 4. 風速の単位と雨の意味

Open-Meteo の風速の既定単位は **km/h**。`fetch_weather.py` と `fetch_forecast_window.py` は `wind_speed_unit` を指定していないため、CSVとJSONの風はkm/h。`score_fog.py` は風速1.5 **m/s** 超を減点する式でその値を使い、`public/forecast.html` も **m/s** と表示する。物理的なスコアと画面表示には単位のズレがある。**モデルは同じkm/hの数値で学習・予測しているため、単位表示のズレだけがAIの外れの原因だとは断定しない。** 単位を変更してAIに入れるなら、過去データとモデルを同時にそろえ、検証後に採用する。

APIの `precipitation` は雨・にわか雨・雪の合計で、各時刻の値は**その時刻までの1時間の降水量**。現在の `rain` 列は朝5～8時の `precipitation` の平均で、雨だけの有無や前日の降水量合計ではない。`docs/02_Technical_Design_SkyCastle.md` は `rain` を「前日降水量合計」と説明する箇所があり、実コードと違う。当日の雨・雪、観察時刻、前夜の雨は分けて扱う。朝の平均値が0より大きいというだけで出現率を0%にすると、現地の観測とAPIの推定値のズレで出現日を消す危険がある。

## 過去の時間別API調査と日本時間

Open-Meteo Historical Weather APIへ `timezone=Asia/Tokyo`、`wind_speed_unit=ms` を指定して読み取り調査した。API返答は `timezone: Asia/Tokyo`、`utc_offset_seconds: 32400`、時刻 `2025-11-04T07:00` のように日本時間。**予測コードも `timezone=Asia/Tokyo` を指定しているため、5～8時は日本時間。** ただし、普段の予測コードは `wind_speed_unit=ms` を指定していない。

2025年10月27日～2026年2月5日の時間別の過去の天気を同じ座標で比べた。城を確認した12日のうち、午前0～1時のAPIの雨が0より大きい日が2日（2025年12月28日、2026年2月5日）。どちらも7～8時のAPIの雨は0。**午前0～1時の雨だけで出現を絶対に除外できない。** 出現12日の7～8時の雲量中央値は約36%、出現しなかった86日の約89%より低かった。城を確認した2025年12月2日は、8時のAPI降水量が0.1 mm、天気コード51。城の観測とAPIの雨推定値が食い違う例なので、「APIの雨予報があれば必ず実際に雨が降る」とは扱えない。時間別の値でも観察の正確な時刻と現地の雨が一致する保証はない。

このAPIは現地で直接測った天気ではなく気象モデルによる**過去の天気の推定値**。実際の予測を評価するには、出現後に分かった天気ではなく、当時利用できた予報を使う。Git履歴に当時の予測JSONと朝平均の予報が残っている。APIを使って更に時間別の過去予報を調べる場合は、Open-Meteoの Previous Runs API（固定の予報先行時間）または Single Runs API（個別の発表時点）を使う。過去の天気APIだけで80～100%を達成したと判断しない。

## 的中率80～100%を目指すための方針

2026年9月15日までの毎日の観測記録では、「天空の城チャンス」に相当する `Castle` 予想は41日、的中は9日、外れは32日だった。そのため、現在の的中率は **9÷41＝22.0%**。実際に天空の城を確認した12日のうち9日を予想できており、出現日を発見できた割合は **9÷12＝75.0%**、見逃しは3日だった。

現在の9日の的中を維持したまま的中率80%にするには、`Castle` 予想を最大11日程度まで絞り、32日ある外れを2日程度まで減らす必要がある。100%なら外れを0日にしなければならない。ただし、予報を年1回だけ出して的中した場合でも100%になるため、的中率だけで予報の良さを判断しない。

今後は、天空の城と霧のそれぞれについて、次の数値を必ず一緒に比較する。

- 予報を出した回数
- 的中回数
- 外れ回数
- 見逃し回数
- 実際の出現回数

当面は、的中率40%以上と出現発見率60%以上、次に的中率60%以上と出現発見率60%以上を段階的に目指す。最終目標は的中率80%以上とするが、100%を保証せず、見逃しとのバランスを重視する。

### 優先する施策

1. **前日データの不具合を直す**
   - 最初の予報日より後の履歴を「前日」として使わない。
   - 本当の1日前のデータがある場合だけ利用し、日付が飛んでいる行も無条件に前日扱いしない。
2. **当時の予報を上書きせず保存する**
   - 予報を作った日時、予報対象日、AIの確率、event、時間別の気象予報を保存する。
   - 予報値と後日の観測結果を別々に残し、履歴データで過去の予報を上書きしない。
3. **月・季節などをAI入力に追加する**
   - 月、季節、年間の通算日、日の出時刻などを候補とする。
   - 「夏だから必ず0%」のような固定ルールにはせず、学習に使っていない日付で効果を確認する。
4. **朝の平均値を時間帯別に分ける**
   - 前日の日中、前日18～24時、当日0～1時、2～4時、5～6時、7～8時を分けて調べる。
   - 夜間の最低気温、気温低下量、時間ごとの湿度、風速、雲量、雨がやんでからの時間、前日降水量、露点差を候補とする。
5. **霧と天空の城を段階的に予測する**
   - 「盆地に霧が発生する」「城が霧の上に出る」「観察時間に城が見える」の3段階を分ける。
   - 「霧は出たが濃すぎて城が見えない」と「霧が出ない」も分けて記録する。
6. **古い選別データと毎日の連続データを区別する**
   - 2015～2025年の意図して集めたデータと、2025年10月27日以降の毎日データを同じ発生割合として扱わない。
   - 毎日の連続記録を主な評価データにし、必要なら古いデータの学習時の重みを下げる。
7. **高確率の日だけを「天空の城チャンス」にする**
   - 現在の50%基準を固定で使わず、未学習期間の検証結果から基準を選ぶ。
   - 「天空の城チャンス」「天空の城候補」「霧海の予感」のように表示を分け、強い表示は非常に条件が良い日だけに限定する。

### 検証と実行の順番

1. 現行モデルの予報数、的中、外れ、見逃しを基準値として保存する。
2. 前日データの不具合を直した場合の予測差を比較する。
3. 過去予報を上書きしない保存方式を作る。
4. ランダムに混ぜず、古い期間で学習し、それより新しい未学習期間で検証する。
5. 季節、時間帯別データ、古いデータの重みを順番に変え、どの施策が効いたか分かるように比較する。
6. 複数の確率基準を比較し、的中率と見逃しのバランスが良い設定を選ぶ。
7. 実際の前夜予報で数か月検証してから、新しいモデルを採用する。

いきなり再学習すると、学習データ上の数字だけが良く、実際の予報では当たらないモデルになる危険がある。そのため、最初に正しい検証方法を作り、各変更の効果を一つずつ確認する。

### 2017年以降の出現記録と霧だけの記録の扱い

ユーザーから、2017年以降のデータは天空の城の出現記録であり、霧だけのデータが混ざっている可能性があるため、それは除外して使うという方針が示された。

2026年9月18日時点の`data/history.csv`を確認した。2017年9月8日以降は564行あり、2025年10月23日までの古い期間は237行。この古い期間には次が含まれる。

- `castle_visible=1`の天空の城出現日：86日
- `fog_observed=1`かつ`castle_visible=0`の霧だけの日：36日

現在の`build_daily_history_dataset.py`は、`castle_visible=1`の日だけを天空の城の出現日として抽出している。そのため、霧だけの36日は天空の城の正解例からすでに除外されている。2025年10月27日以降の連続観測期間には天空の城12日があり、古い86日と合わせて、全期間の天空の城出現例は98日となる。

`event`列は実際の観測結果ではなく、その時点の予測表示が入る場合がある。実際に、`castle_visible=1`なのに`event=FogOnly`の行や、`castle_visible=0`なのに`event=Castle`の行がある。そのため、出現日の抽出に`event`を使わず、実際の観測結果である`castle_visible`を正解として使う。`fog_observed=1`でも`castle_visible=0`なら霧だけの日として、天空の城の出現例には含めない。

この整理により、過去86例は天空の城になる気象パターンの学習に利用でき、最新12例は未学習期間の最終検証に利用できる。ただし、確率60%、80%、90%という表示を信頼できる値にするには、モデルが出した確率帯と実際の出現割合が一致するかを別に検証する必要がある。

### 60%、80%、90%を信頼できる確率として表示できるかの検証

最良候補の点推定は42.9%だが、対象が7日しかないため、本当の的中率として考えられる範囲は15.8%～75.0%と広い。60%の可能性を否定する結果ではないが、「明日は60%」と信頼できる数字として表示する根拠にもまだならない。80%や90%を裏付ける実績はない。

天空の城は年間約10回の珍しい現象で、全日を対象にすると基本の出現割合は約3%。通常の確率校正はこの低い基本割合を反映するため、現在の特徴量では最大約11%になった。一方、上位候補だけの実績は36～43%である。今後は、日ごとの校正確率と「条件が良い候補群の過去的中率」を混同せずに表示する必要がある。

60%、80%、90%を科学的に表示するには、同じ固定条件で今後のシーズンを前向き検証し、高確率帯に十分な予報件数と的中数を集める必要がある。現時点で数字を60%以上へ引き上げる補正を行うと、実績より大きな確率を表示することになるため、本番へは反映しない。

### 過去の出現日に似た気象条件から確率を出す検証

`evaluate_analog_probability.py`を追加した。2017年以降の全日から、明日の予報に気象条件が近い日を探し、その中で天空の城が出現した割合を確率として使う方法を検証した。霧だけの日は天空の城の正解に含めていない。

類似日の候補は2024年8月までの2,557日で、天空の城は76日。予報側はJMA、ECMWF、両者の平均を比較し、類似日数は20日、30日、50日、100日を比較した。調整期間だけでBrierスコアが最も良い方法を選び、最終検証期間は方法選びに使わなかった。

調整期間で選ばれた方法は「JMAとECMWFの平均条件に近い過去100日」だった。

- 調整期間：365日、出現10日、Brier 0.0252、AP 0.146、最大確率18.2%。
- 最終検証：371日、出現12日、Brier 0.0273、AP 0.317、最大確率20.1%。

最終検証の確率帯は次のとおり。

| 類似日から出した確率帯 | 日数 | 平均予測 | 実際の出現 | 実際の割合 |
| --- | ---: | ---: | ---: | ---: |
| 0～10%未満 | 340日 | 2.2% | 3日 | 0.9% |
| 10～20%未満 | 30日 | 12.8% | 8日 | 26.7% |
| 20～30%未満 | 1日 | 20.1% | 1日 | 100% |

最も高かった2025年11月14日は20.1%で、実際に天空の城が出現した。過去100日の類似日中21日が天空の城だった。2025年11月4日は14.4%で出現、11月15日と11月6日は13.5%と12.5%で出現した。

類似日予測は、高い候補へ出現日を集める効果があった。特に10～20%予測の実際の出現割合は26.7%で、予測値より高かったため、現在の計算はやや控えめ。ただし、過去の類似日20～100日のどの方法でも最大確率は調整期間で約18～26%だった。60%以上になるほど、類似日の大半が天空の城だった組み合わせは確認できなかった。

類似日が少ない場合に2/2を100%と表示することを避けるため、過去全体の発生割合を5日分だけ加える補正を使用した。これにより、少数例による極端な100%を防いでいる。

この結果から、過去の出現日との類似性は予報理由の説明と候補日の順位付けに有効だが、それだけで60～90%を科学的に表示する根拠にはならない。今後は類似日確率をJMA＋ECMWFの固定条件と併用し、2026年秋以降の前向き実績で再校正する。本番処理にはまだ反映していない。

### 条件が似ていたのに出現しなかった5日の原因調査

年間約15日基準で選ばれた8日のうち、的中3日と外れ5日のJMA・ECMWF予報、高さ別雲量、`history.csv`の実際の観測結果を比較した。

外れ5日の実際の結果は次のとおり。

| 日付 | 霧の観測 | 天空の城 | ECMWF低層雲予報 | 中層雲 | 高層雲 | 推定される主な失敗 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 2025年11月12日 | なし | なし | 0% | 0% | 0% | 霧が形成されなかった |
| 2025年11月20日 | なし | なし | 5.0% | 4.7% | 0% | 霧が形成されなかった |
| 2025年11月29日 | あり | なし | 29.0% | 0% | 0% | 霧は出たが城が見えなかった |
| 2025年12月23日 | なし | なし | 3.7% | 0% | 0% | 霧が形成されなかった |
| 2026年2月17日 | なし | なし | 2.0% | 0% | 65.0% | 霧がなく、上空の雲も多かった |

外れ5日のうち4日は`fog_observed=0`で、天空の城以前に盆地の霧が発生しなかった。2025年11月29日だけは`fog_observed=1`、`castle_visible=0`で、霧は出たが城が見えない失敗だった。

的中3日のECMWF低層雲中央値は40.3%、外れ5日は3.7%。JMAの午前5～6時総雲量中央値も、的中30.5%、外れ2.0%。ECMWFの午前5～6時湿度中央値は、的中90.0%、外れ87.5%。ECMWFの午前5～6時風速中央値は、的中2.65km/h、外れ4.35km/hだった。

この少数例では、的中日は「湿度が少し高い」「風がより弱い」「低層の霧・雲が予報されている」傾向がある。外れ日は地上の冷え込みなどは良好でも、実際には霧が形成されない場合が多かった。2026年2月17日は高層雲予報65%で、中層・高層雲60%以下の条件により除外できた。

一方、2025年11月15日はECMWFの低層雲予報0%でも実際に天空の城が出現した。そのため、低層雲が少ない予報を一律に除外すると的中日も消える。低層雲20%以上の条件が最終期間では良くても調整期間で再現しなかった理由の一つと考えられる。

現在の主な誤りは、次の2段階に分けられる。

1. 湿度・冷え込みなどの条件は似ているが、実際には盆地の霧が形成されない。
2. 霧は形成されたが、霧の高さ・濃さ・視界のため城が見えない。

今後は一つの確率でまとめず、まず「盆地に霧ができる確率」、次に「霧がある場合に城が見える確率」を分けて推定する方法が必要。特に、現在の外れの多くを占める霧形成の判定改善が優先となる。

### 前日JMA予報による「霧→城」の2段階モデル検証

`evaluate_two_stage_model.py`を追加し、前日のJMA MSM予報を使って次の2段階を別々に学習した。

1. 盆地に霧が発生する確率。
2. 霧が発生した場合に天空の城が見える確率。

最終的な値は、この2つを掛けて計算した。ECMWFは学習期間に4日しかなく、学習に使える量ではないため、この検証ではJMAだけを使用した。

使用できた件数は次のとおり。

- 学習：62日、霧33日、天空の城25日。
- 調整：43日、霧25日、天空の城10日。
- 最終検証：毎日の連続記録321日、霧17日、天空の城12日。

第2段階のLightGBMは、学習件数が33日と少なすぎて全日に50%の一定値を返した。このようなモデルは不採用とし、日ごとの差を出せるロジスティック回帰を使用した。

最終検証の順位比較は次のとおり。

| 方法 | AP | AUC | 上位5日 | 上位10日 | 上位15日 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 天空の城を直接予測 | 0.215 | 0.799 | 1/5 | 1/10 | 4/15（26.7%） |
| 霧→城の2段階予測 | 0.127 | 0.861 | 0/5 | 1/10 | 1/15（6.7%） |

2段階予測はAUCでは上がったが、高い順位へ実際の出現日を集めるAPと上位日の的中率は悪化した。観光向けに重要な「高い予報を出した日の的中率」は直接予測より低かった。

2段階モデルが出した未校正の高い数字と、実際の成績は次のとおり。

| モデル表示 | 予報数 | 的中 | 実際の的中率 |
| --- | ---: | ---: | ---: |
| 50%以上 | 31日 | 3日 | 9.7% |
| 60%以上 | 13日 | 1日 | 7.7% |
| 70%以上 | 1日 | 0日 | 0% |
| 80%以上 | 0日 | 0日 | － |
| 90%以上 | 0日 | 0日 | － |

2026年2月5日の出現日は、霧86.5%、霧がある場合の城73.8%、組み合わせ63.9%となり的中した。しかし、60%以上を出した13日全体では1日しか的中していない。そのため、2段階に分ければ60%以上の数字自体は作れるが、その数字は実際の60%を意味しない。

2段階という科学的な考え方は妥当だが、現在の古い記録は毎日の連続データではなく、霧モデルの学習62日、条件付きの城モデル33日では少なすぎる。特に第1段階の霧予測は、最終期間でAP 0.115、Brier 0.273にとどまった。現時点では2段階モデルを本番へ採用せず、直接予測とJMA＋ECMWFの固定候補を維持する。

今後2段階モデルを成立させるには、毎日の前夜予報と翌朝の「霧なし・霧だけ・天空の城」を同じ方法で継続保存し、各段階の学習件数を増やす必要がある。

### 観測入力の運用方針（2026年9月18日）

運用者は毎日出現を確認しているため、ダッシュボードへの入力は出現した日だけに限定する。入力のない日は「未確認」ではなく、霧も天空の城も出なかった「不出現」として扱う。

出現時の入力は「天空の城が出た」と「霧だけ出た」の2種類とする。霧だけの記録は、「霧が発生する条件」と「霧があるときに城が見える条件」を分けて検証するために保存する。

`dashboard.py`の観測入力は、2つのチェックボックスと保存ボタンの組み合わせから、2つの出現ボタンのどちらかを押す方式に変更した。天空の城は`fog_observed=1, castle_visible=1`、霧だけは`fog_observed=1, castle_visible=0`として保存する。新規日付を手入力するときは、過去の平均気象値を実測値のように入れず、実際の気象データがない項目は空欄で保存する。

過去データの一覧は、最近の記録をすぐ確認できるよう、ダッシュボード上では日付の新しい順に表示するよう変更した。CSVを保存するときは、従来どおり日付の古い順に戻す。

ダッシュボードの「過去推移グラフ」は、運用に不要となったため表示と専用処理を削除した。`data/history.csv`などの過去データは削除していない。

ダッシュボード下部の「手動実行」は、日常の観測入力に不要なため削除した。画面から「最新予報を再計算」と「指定日の気象データを取得」は実行できなくなる。予報の自動処理と、過去データ表の「テーブルの変更を保存」ボタンは残している。

過去データ表は、予測判定を日付と一緒に確認しやすくするため、画面上で`event`列を`date`列のすぐ右に表示するよう変更した。表を編集して保存するときは、CSVの列順を従来の順番に戻す。

### 9月18日の70%表示の原因確認（2026年9月18日）

9月18日の従来AIの総合値は69.6%だったが、朝5～8時の予報気温は20.7℃、湿度83.25%、風速4.2km/h、雲量30%、雨0mmだった。運用者から、気温20.7℃では放射冷却による条件として不自然ではないかとの指摘があった。

再計算して確認したところ、従来AIは雲海率79.1%、天空率76.7%を出し、最後の調整計算で総合69.6%にしていた。高くなった直接の理由は、前日の同時刻の湿度97%、弱風、晴れ、雨なしを強く評価したためである。

ただし、従来AIの入力にある`temp_prev_diff`は「前日の朝5～8時平均との差」であり、放射冷却に重要な夕方から明け方までの気温低下ではない。夜間の最低気温、夕方の気温、夜間の雲量変化を使っていないため、放射冷却が起こるかを科学的に判定できない。月・季節も入力にない。実際に、過去の9月で朝5～8時の気温が19～22℃だった近い条件の表示例を確認すると、抽出した直近20日はすべて天空の城の不出現日だった。

したがって、この70%は信頼できる出現確率ではなく、従来AIの弱点が表れた数値である。20.7℃だけで放射冷却が絶対に起きないとは断定できないが、現在の予報システムには放射冷却を判定するための必要な夜間データがなく、70%を出す根拠としては不十分である。

### 科学条件モデルの事前検証（2026年9月18日）

公開画面は変更せず、過去の毎日データにある夜間条件で検証した。使った条件は、前夜18～23時の雨、深夜の雨、午前2～4時の最低気温、前夜から午前4時までの冷え込み、午前5～6時の湿度・風・雲・露点差・雨、午前6～8時の雲・風・雨、および季節である。

2017年9月～2024年8月の2,557日・出現76日で学習し、2024年9月～2025年8月の365日・出現10日で表示基準を決めた。その基準を変えずに、2025年9月～2026年9月17日の382日・出現12日で最終検証した。

| 検証方法 | 上位5日 | 上位10日 | 上位15日 | AUC |
|---|---:|---:|---:|---:|
| 実際の時間別気象を使用 | 1/5（20%） | 3/10（30%） | 4/15（26.7%） | 0.923 |
| 前夜ECMWF予報を使用 | 1/5（20%） | 2/10（20%） | 3/15（20%） | 0.904 |

実際の時間別気象を使う場合は、夜間条件を含めることで出現日を並べる力があることを確認できた。ただし、前夜の予報に置き換えると精度は下がり、60%以上の確率を約束できる状態にはまだない。単純な条件ルールでも、未来を使わない検証で4/12（33.3%）にとどまった。

気温だけでの除外は行わない。9月18日の20.7℃は朝5～8時の平均気温で、夜中の最低気温ではない。過去98出現日のうち、午前2～4時の最低気温が12℃を超えた日は6日あり、2019年10月1日は19.7℃だった。放射冷却や出現可能性は、最低気温だけではなく、前夜からの冷え込み、湿度、露点差、風、夜間・早朝の雲、雨、朝の見通しを組み合わせて判断する必要がある。

今回確認できた結論は、「現行AIの70%をそのまま信じることはできないが、気温だけで0%にもできない」である。次段階では、毎晩同じ時刻の14日予報を保存し、何日前の予報だったか別に、実際の結果と比較するデータを蓄積する。これにより、旅行者向けの7～14日予報についても、将来は実績で校正した確率を出せるようにする。

`build_history_expectations.py`と`public/data/history_expectations.json`を追加した。振り返りAIは、各月についてその月より前の記録だけで学習し、当日の実際の時間別気象を入力する。未来の正解を学習に含めない。これは当時公開された予報値の再現ではなく、実際の気象から過去を振り返る参考値である。

### 期待指数の計算方法をAI推定値基準へ変更

当初の季節順位だけの指数では、天空の城がほとんど出ない3月でも、春夏の中で相対的に上位という理由で95や100になる問題があった。AI予測値の単純な2倍・3倍も比較したが、実際に天空の城が出た日まで低く抑えすぎた。また、季節順位と月別上限の低い方、季節順位に月別係数を掛ける方法も試したが、AI推定値3%で指数70になるなど、利用者に分かりにくい結果が残った。

最終的に、期待指数はAI推定値を直接基準にし、過去実績から決めた次の基準点の間を補間して5刻みに丸める方式とした。

| AI推定値 | 期待指数の基準点 |
|---:|---:|
| 0% | 0 |
| 3% | 20 |
| 8% | 50 |
| 20% | 80 |
| 50%以上 | 100 |

さらに、最も出現率が高い月を100として、月ごとの過去出現率から指数上限を作る。これにより、AI推定値が一時的に高くても、出現実績が少ない3月などで指数95や100を表示しない。同じ季節の過去AI予測に対する上位順位は、指数計算には使わず、詳細画面の参考情報として残す。

この方式では、確認時点の予報は10月2日がAI推定値8.0%・指数50、10月5日がAI推定値3.8%・指数25となった。過去ログでは、1月6日のAI推定値6.2%は指数40、11月17日の3.0%は指数20となり、低いAI推定値なのに指数だけが高い問題を改善した。3月11日と17日はAI推定値が約30%でも月別上限により指数40となった。

### 過去333件による期待指数の確認

333件のうち、時間別特徴量がそろっていた326件で、未来の正解を使わない振り返り指数を確認した。天空の城は12日、霧のみは5日だった。

| 期待指数 | 日数 | 天空の城 | 実際の出現率 |
|---|---:|---:|---:|
| 0～20 | 271日 | 2日 | 0.7% |
| 21～49 | 35日 | 4日 | 11.4% |
| 50～79 | 16日 | 3日 | 18.8% |
| 80～100 | 4日 | 3日 | 75.0% |

指数が高いほど実際の出現率も上がった。ただし80以上は4件しかなく、今後も75%で当たると断定できない。指数50以上は20日中6日で天空の城、1日で霧のみだった。振り返り指数は実際の気象を入力するため、未来の天気予報を入力する本番より良く見える可能性がある。計算式は当面固定し、次の秋冬の記録を蓄積してから再検証する。

### 最近の過去ログへ期待指数を自動追加

`data/analysis/daily_history_2017_2026.csv`が2026年9月17日で止まっていたため、9月18日～24日のカードには期待指数がなかった。Open-Meteoから7日分の時間別気象を取得し、AI用データを3,304日から3,311日へ増やした。科学条件AIが使う16特徴量には空欄がないことを確認した。

`build_daily_history_dataset.py`は、固定終了日を廃止し、日本時間の当日または`--end-date`で指定した日までを対象にした。既存CSV全体を書き直さず、未取得の日だけを末尾へ追加する。GitHub Actionsの11時5分の日次処理では、観測履歴更新後に時間別AIデータを追加し、`build_history_expectations.py`で公開用の振り返り指数を再生成する。更新した分析CSVも自動コミット対象に加えた。

ローカルMacではLightGBMが必要とする`libomp.dylib`がないため、最終的な期待指数JSONの再生成はできなかった。時間別データの取得と入力検証までは完了しており、Linuxで動くGitHub Actionsで`public/data/history_expectations.json`を更新する運用とする。
